# Deploying to Cloudflare

This project is a TanStack Start app built by Vite and bundled for Cloudflare Workers by Nitro's
`cloudflare-module` preset. Deployment is a Worker with a static-assets binding — not Cloudflare
Pages.

## Prerequisites

- **Node.js 20 or newer.** `vite@^8` and `nitro@3.x-beta` both require it. The repo pins Node via
  `.node-version` (`22`) and declares `"engines": { "node": ">=20" }`.
- **Bun** as the package manager, pinned via `"packageManager": "bun@1.2.14"`. Only `bun.lock` is
  committed; there is no `package-lock.json`. Install with `bun install`.

Cloudflare's build image does not always honour `.node-version`. If a build reports an
older Node, also set a **`NODE_VERSION`** build environment variable (e.g. `22`) in the Cloudflare
dashboard under **Workers & Pages → your project → Settings → Build**.

## Build and deploy

```sh
bun install
bun run build       # vite build
bunx wrangler deploy
```

Or in one step, from the project root:

```sh
bun run deploy      # vite build && wrangler deploy
bun run cf:preview  # vite build && wrangler dev
```

Cloudflare build settings:

| Setting        | Value             |
| -------------- | ----------------- |
| Build command  | `bun run build`   |
| Deploy command | `wrangler deploy` |
| Root directory | repository root   |

The build writes to `.output/` (git-ignored):

- `.output/server/index.mjs` — Worker entry.
- `.output/public/` — static assets, served through the `ASSETS` binding.
- `.output/server/wrangler.json` — Worker config generated by the preset (`nodejs_compat`,
  assets binding, compatibility date).
- `.wrangler/deploy/config.json` — points Wrangler at the generated config above.

### Always run Wrangler from the project root

Wrangler discovers the generated config through `.wrangler/deploy/config.json`, whose
`configPath` is relative to the repository root. Running Wrangler from inside `.output/server`
fails with:

```
Found both a user configuration file at ... and a deploy configuration file at ...,
but these do not share the same base path.
```

Do **not** add a hand-written `wrangler.toml` or `wrangler.jsonc` at the repo root to work around
this. It would conflict with the generated config and produce the same error. Just stay in the
project root.

## Environment variables

Supabase configuration is read in two places and needs to be set in **two different scopes**.
Getting this wrong produces a green build and a broken site.

### Build-time (required for the browser bundle)

Vite inlines `VITE_*` values into the client bundle when `vite build` runs, so these must exist in
Cloudflare's **build** environment — setting them only as Worker runtime secrets is too late.

| Variable                        | Purpose                                |
| ------------------------------- | -------------------------------------- |
| `VITE_SUPABASE_URL`             | Supabase project URL                   |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Publishable / anon key                 |
| `VITE_SUPABASE_PROJECT_ID`      | Project ref, used by generated clients |

If these are missing, the build still succeeds — `src/integrations/supabase/client.ts` builds its
client lazily behind a `Proxy`. The failure surfaces at runtime instead: the first Supabase call
throws `Missing Supabase environment variable(s)`.

### Runtime (required for SSR and the sitemap)

Set these as Worker variables (`wrangler secret put <NAME>`, or the dashboard under
**Settings → Variables and Secrets**).

| Variable                        | Read by                                             |
| ------------------------------- | --------------------------------------------------- |
| `SUPABASE_URL`                  | `src/integrations/supabase/client.ts`, SSR fallback |
| `SUPABASE_PUBLISHABLE_KEY`      | `src/integrations/supabase/client.ts`, SSR fallback |
| `VITE_SUPABASE_URL`             | `src/routes/sitemap[.]xml.ts`, via `process.env`    |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | `src/routes/sitemap[.]xml.ts`, via `process.env`    |

Both spellings are genuinely consulted, and they are not interchangeable:

- `client.ts` falls back to the **un-prefixed** names (`process.env.SUPABASE_URL`,
  `process.env.SUPABASE_PUBLISHABLE_KEY`) when the inlined `VITE_*` values are absent.
- The sitemap handler reads the **`VITE_`-prefixed** names from `process.env` first, falling back to
  `import.meta.env`.

The safe configuration is to set all four runtime variables — the two un-prefixed and the two
`VITE_`-prefixed — alongside the three build-time variables.

### Never expose the service-role key

> **Warning:** never set `SUPABASE_SERVICE_ROLE_KEY` — or any other secret — as a `VITE_*`
> variable. Any `VITE_`-prefixed value is inlined into the client bundle and served to every
> visitor. No service-role key belongs in this project's client bundle at all; this app talks to
> Supabase exclusively with the publishable key plus row-level security.

## Local setup

Copy `.env.example` to `.env` and fill in the values from your Supabase project
(**Supabase dashboard → Project Settings → API**). `.env` is git-ignored. See `.env.example` for the
authoritative list of variables and notes.
